# Правила коммитов и отправки StackCard

Git-команды выполняются из корня monorepo в macOS zsh/bash. Эти правила действуют для каждого фактического commit независимо от инструмента его создания. Перед Git-операциями прочитай этот файл.

## Нативный commit-msg hook

Версионируемый [.githooks/commit-msg](../../.githooks/commit-msg) вызывает
[project validator](../../tools/git/validate_commit_message.py) через Python 3.
Он не зависит от Codex и проверяет коммиты из Desktop Commit, IDE и терминала:
русский Conventional Commit, body и точное совпадение каждого пути с prospective
Git index. Rename считается удалением старого и добавлением нового пути;
для каждого нужен отдельный пункт с непустым описанием. Missing/extra/duplicate
пути и ошибки чтения блокируют commit. Никаких ограничений 72/4000 символов нет.
Git editor comments с префиксом `#` удаляются, проверенный текст сохраняется
в message file; нестандартный `core.commentChar/core.commentString` отклоняется.

Установка после clone, macOS zsh/bash или Windows Git Bash, cwd корень monorepo:

```sh
git config --local core.hooksPath .githooks
```

Это локальная настройка checkout: другой clone должен включить hook отдельно.
Проверки без изменения основного репозитория, тот же терминал/cwd:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/git -p 'test_*.py' -v
```

Git не передаёт `--amend` в commit-msg. Поэтому исправление существующего commit
требует явного режима; **не экспортировать** его для следующих обычных commits:

```sh
STACKCARD_COMMIT_MODE=amend git commit --amend -F <message-file>
```

Этот режим сравнивает index с родителем исправляемого HEAD, для первого commit —
с пустым деревом. Обычный режим сравнивает index с HEAD. Пустые commits и amend
merge commit отклоняются. Режим должен соответствовать операции; после создания
всегда проверять фактический объект через `git show` и `git diff-tree --root --no-renames`.
Hook не генерирует описания: если Desktop потерял diff/body, подготовь полное
сообщение по реальным файлам и передай его через `git commit -F`.

ИНСТРУКЦИЯ ПО GIT COMMIT, REBASE, PULL И PUSH
Когда я прошу написать commit, создать commit, закоммитить изменения, отправить изменения, выполнить push, скачать изменения, выполнить pull, синхронизировать ветку или использую слово commit, всегда строго следуй этим правилам.
ГЛАВНЫЙ ПРИНЦИП GIT WORKFLOW
История ветки должна оставаться линейной.
Для получения удалённых изменений всегда используй rebase.
Никогда не используй обычный git pull, если он может создать merge commit.
Никогда не создавай merge commit только ради синхронизации локальной и удалённой ветки.
Перед каждым push обязательно синхронизируй локальную ветку с удалённой через fetch + rebase.
Основной принцип:
локальные изменения -> commit -> fetch -> rebase поверх актуальной удалённой ветки -> push
Если локальные изменения ещё не готовы к commit, но необходимо получить изменения из remote:
stash -> fetch -> rebase -> stash pop
ПОЛУЧЕНИЕ ИЗМЕНЕНИЙ ИЗ REMOTE
При чистом рабочем дереве используй:
git fetch origin
git rebase origin/<current-branch>
Допустимый сокращённый вариант:
git pull --rebase
Обычный:
git pull
не используй.
Если существуют незакоммиченные локальные изменения, сначала временно убери их в stash, включая untracked-файлы:
git stash push -u -m "before-rebase"
После выполнения stash обязательно проверь, что stash действительно был создан.
Только после этого выполняй:
git fetch origin
git rebase origin/<current-branch>
После rebase обязательно убедись, что он успешно завершён.
Только после успешного rebase выполняй:
git stash pop
Не выполняй stash, если рабочее дерево уже чистое.
Не выполняй stash pop до успешного завершения rebase.
Если во время rebase возник конфликт, не выполняй push и не переходи к следующим операциям автоматически.
Разреши конфликт, добавь исправленные файлы:
git add <resolved-files>
Затем продолжи:
git rebase --continue
Повторяй разрешение конфликтов и git rebase --continue до полного завершения rebase.
Не используй git rebase --abort автоматически, если конфликт можно корректно разрешить.
Если после stash pop возник конфликт, разреши его отдельно. Не считай синхронизацию завершённой, пока рабочее дерево не приведено в корректное состояние.
ПРАВИЛА ПЕРЕД COMMIT
Перед каждым commit обязательно проверь текущее состояние репозитория:
git status
После этого обязательно изучи фактический diff:
git diff
Если часть изменений уже находится в staging, дополнительно проверь:
git diff --cached
Нельзя формировать commit message по предположениям, названию задачи, предыдущему контексту или ожидаемым изменениям.
Commit message должен описывать только фактический diff.
Определи полный список изменённых, созданных, удалённых и переименованных файлов.
Если в рабочем дереве находятся посторонние изменения, которые не относятся к текущей задаче, не добавляй их автоматически в commit.
Не используй git add . без предварительной проверки файлов.
Предпочитай явно добавлять только относящиеся к текущей задаче файлы:
git add <file1> <file2> <file3>
После staging обязательно проверь:
git status
git diff --cached
Commit создавай только после того, как убедился, что staged diff содержит именно те изменения, которые должны войти в commit.
ЛОГИЧЕСКОЕ РАЗДЕЛЕНИЕ COMMIT
Один commit должен представлять одно логически целостное изменение.
Если изменения относятся к нескольким независимым задачам, не смешивай их в один commit.
Раздели их на несколько отдельных commit, каждый со своим заголовком и body.
Если несколько файлов относятся к одной задаче или одному функциональному изменению, они должны оставаться в одном commit.
Не создавай бессмысленно мелкие commit на каждый файл.
ФОРМАТ COMMIT
Каждый commit обязан использовать Conventional Commits:
type(scope): description
type и scope — строго на английском языке и только lowercase.
description — строго на русском языке, lowercase, без точки в конце.
Допустимые type:
feat — новый функционал
fix — исправление ошибки
docs — документация
style — форматирование без изменения поведения
refactor — рефакторинг без добавления нового функционала
test — тесты
chore — конфигурация, зависимости, инфраструктурные или служебные изменения
scope должен кратко и точно обозначать область изменений.
Примеры хороших scope:
api
auth
mobile
web
ui
database
docker
config
router
profile
portfolio
docs
ai
deps
redesign
Не используй слишком общий scope вроде app или project, если изменения относятся к более конкретной области.
DESCRIPTION
Description должен быть подробным.
Ориентировочная длина description: 7–25 слов.
Description должен объяснять не только что изменено, но по возможности также как это сделано или зачем.
Используй глаголы только в прошедшем времени, мужском роде, от первого лица.
Примеры допустимых глаголов:
добавил
исправил
настроил
создал
обновил
вынес
переименовал
разбил
переработал
удалил
заменил
подключил
реализовал
перенёс
ограничил
упростил
синхронизировал
зафиксировал
объединил
Не используй формулировки:
добавление
исправление
обновление
реализация
изменения
разные изменения
правки
фикс
update
changes
misc
wip
Не пиши слишком короткие commit messages вроде:
fix(api): исправил ошибку
feat(ui): добавил интерфейс
chore(config): обновил настройки
Commit должен позволять понять основную суть изменения без открытия diff.
Хороший пример:
feat(api): добавил эндпоинт регистрации пользователей, вынеся проверку входных данных в отдельный middleware
Другой пример:
refactor(mobile): вынес правила flutter-приложения в отдельный scope, связав их с общими инструкциями проекта
BODY COMMIT
Body обязателен всегда.
Commit без body запрещён независимо от количества изменённых файлов.
Даже если изменён только один файл, этот файл обязательно должен быть указан в body.
Body должен содержать полный список ВСЕХ файлов, фактически вошедших в commit:
изменённых
созданных
удалённых
переименованных
Не пропускай служебные, конфигурационные, документационные, lock-файлы или автоматически изменённые файлы, если они реально входят в commit.
Для каждого файла создавай отдельную строку.
Формат:
- path/to/file.ts: конкретное описание изменения в этом файле
Путь всегда указывай относительно корня репозитория.
Описание должно объяснять, что именно изменилось в конкретном файле.
Не объединяй несколько файлов в одну строку.
Неправильно:
- src/auth/*: обновил авторизацию
Правильно:
- src/auth/auth.controller.ts: добавил эндпоинт регистрации и передачу входных данных в auth service
- src/auth/auth.service.ts: добавил создание пользователя и проверку существующего email
- src/auth/auth.dto.ts: добавил правила валидации имени, email и пароля
Если файл создан, явно укажи, что именно в нём создано.
Если файл удалён, явно укажи, что он удалён, и причину, если она понятна из diff.
Если файл переименован или перенесён, явно укажи перенос или переименование и новое назначение либо расположение.
Body должен позволять понять структуру commit без открытия diff.
ФОРМАТ ПОЛНОГО COMMIT MESSAGE
Каждый фактический commit должен иметь именно такую структуру:
type(scope): подробное описание на русском языке
- path/to/first-file.ts: конкретное описание изменения первого файла
- path/to/second-file.ts: конкретное описание изменения второго файла
- path/to/third-file.ts: конкретное описание изменения третьего файла
Между заголовком и первой строкой body должна быть ровно одна пустая строка.
То есть фактическое сообщение должно выглядеть так:
type(scope): подробное описание на русском языке

- path/to/first-file.ts: конкретное описание изменения первого файла
- path/to/second-file.ts: конкретное описание изменения второго файла
КРИТИЧЕСКОЕ ПРАВИЛО ЗАПИСИ BODY В GIT
Недостаточно сформировать body в ответе, плане, комментарии, внутреннем рассуждении или описании выполненной работы.
Body должен быть ФАКТИЧЕСКИ записан внутрь объекта Git commit.
Commit, внутри которого сохранён только subject, считается неправильным и незавершённым.
Запрещено создавать итоговый commit только командой вида:
git commit -m "type(scope): description"
Такая команда передаёт Git только subject и не создаёт требуемый body.
Перед выполнением git commit сначала полностью сформируй итоговое сообщение:
subject
пустая строка
body со всеми файлами
После этого передай Git ВСЁ многострочное сообщение целиком, а не только первую строку.
Предпочтительный надёжный способ — использовать временный файл с полным commit message:
git commit -F <message-file>
Содержимое временного файла должно иметь вид:
type(scope): подробное описание на русском языке

- path/to/file1: описание изменения
- path/to/file2: описание изменения
- path/to/file3: описание изменения
Разрешается использовать несколько параметров -m, только если итоговый объект Git commit действительно получает полный subject и полный body.
Например, технически допустим формат:
git commit -m "type(scope): description" -m "- path/to/file1: описание изменения
- path/to/file2: описание изменения"
Но способ через commit message file предпочтительнее, если shell, терминал или агент может некорректно обработать многострочный аргумент.
Критерием правильности является не команда, использованная для создания commit, а фактическое содержимое объекта Git commit.
ПРОВЕРКА COMMIT ПОСЛЕ СОЗДАНИЯ
Сразу после каждого git commit обязательно проверь фактически записанное полное сообщение:
git show -s --format=full HEAD
или:
git log -1 --format=full
В выводе должны фактически присутствовать:
1. полный subject;
2. пустая строка после subject;
3. body;
4. отдельная строка body для каждого файла commit.
После этого обязательно проверь фактический список файлов commit:
git diff-tree --no-commit-id --name-status -r HEAD
При необходимости также используй:
git show --stat --oneline HEAD
Сверь фактический список файлов commit со списком файлов, указанным в body.
Каждый файл из commit должен присутствовать в body.
В body не должно быть файлов, которые фактически не вошли в commit.
Если body отсутствует, обрезан, содержит не все файлы или commit был создан только с subject, задача НЕ считается выполненной.
Если неправильный commit ещё не был опубликован в remote, исправь его через:
git commit --amend
При amend также обязательно сохрани полный subject + пустую строку + body.
После amend снова выполни:
git show -s --format=full HEAD
git diff-tree --no-commit-id --name-status -r HEAD
И снова сверь body с фактическим содержимым commit.
Если commit уже опубликован в remote, не переписывай опубликованную историю автоматически.
Сообщи пользователю о проблеме и дождись явного разрешения на переписывание опубликованной истории.
ПРАВИЛА ВЫВОДА COMMIT MESSAGE
Если я прошу только написать commit message, не выполняй Git-команды.
Сначала, если у тебя есть доступ к репозиторию, проанализируй git status и git diff.
Если доступа к фактическому diff нет, не выдумывай список файлов. Попроси предоставить diff или данные, необходимые для точного commit message.
Если фактический diff известен, выводи сразу готовый commit message без вводных фраз.
Не добавляй перед ним:
"вот коммит"
"можно использовать такой commit"
"предлагаю следующий commit"
"готовый вариант"
Результат должен сразу начинаться с:
type(scope): description
Затем одна пустая строка и полный body.
COMMIT БЕЗ PUSH
Если я прошу реально закоммитить изменения:
1. выполнить git status;
2. проверить git diff;
3. проверить git diff --cached, если staging уже существует;
4. определить логическую область текущей задачи;
5. определить полный список файлов, относящихся к задаче;
6. не включать посторонние изменения;
7. явно добавить необходимые файлы в staging;
8. проверить git status;
9. проверить git diff --cached;
10. сформировать полный commit message: subject + пустая строка + body;
11. записать в Git полный commit message, а не только subject;
12. выполнить git show -s --format=full HEAD;
13. выполнить git diff-tree --no-commit-id --name-status -r HEAD;
14. убедиться, что body реально существует и перечисляет все файлы commit;
15. только после этой проверки считать commit успешно созданным.
COMMIT И PUSH
Если я прошу закоммитить и отправить изменения, порядок строго следующий:
1. выполнить git status;
2. проверить фактический git diff;
3. проверить git diff --cached, если staging уже существует;
4. определить полный список файлов текущей логической задачи;
5. исключить посторонние изменения;
6. явно добавить нужные файлы в staging;
7. проверить git status;
8. проверить git diff --cached;
9. сформировать Conventional Commit по всем правилам;
10. сформировать обязательный body со ВСЕМИ файлами commit;
11. создать commit, фактически записав subject + пустую строку + body в объект Git commit;
12. выполнить git show -s --format=full HEAD;
13. выполнить git diff-tree --no-commit-id --name-status -r HEAD;
14. убедиться, что commit содержит body и body соответствует фактическому списку файлов;
15. определить текущую ветку;
16. выполнить git fetch origin;
17. выполнить git rebase origin/<current-branch>;
18. если возникли конфликты, корректно разрешить их и завершить rebase через git rebase --continue;
19. убедиться, что rebase полностью завершён;
20. выполнить git push origin <current-branch>;
21. проверить, что push завершился успешно;
22. не считать задачу завершённой, если commit, rebase или push завершились ошибкой.
PUSH
Перед каждым push обязательно выполняй:
git fetch origin
git rebase origin/<current-branch>
git push origin <current-branch>
Если push был отклонён, потому что remote изменился между rebase и push, не используй force.
Повтори:
git fetch origin
git rebase origin/<current-branch>
git push origin <current-branch>
Если rebase вызывает конфликты, сначала полностью разреши их.
Не выполняй push при незавершённом rebase.
Не выполняй push при известных неразрешённых конфликтах.
FORCE PUSH
Никогда не используй:
git push --force
Без прямого разрешения пользователя не переписывай опубликованную историю.
Если после осознанного rebase опубликованной ветки действительно требуется принудительная отправка и пользователь явно разрешил переписывание истории, используй только:
git push --force-with-lease origin <current-branch>
Никогда не используй --force вместо --force-with-lease.
ПРАВИЛА БЕЗОПАСНОСТИ
Никогда автоматически не удаляй локальные изменения.
Никогда не выполняй git reset --hard для решения проблем синхронизации.
Никогда не выполняй git clean -fd без прямого запроса пользователя.
Никогда не удаляй stash, пока не убедился, что изменения успешно восстановлены.
Никогда не выполняй push при незавершённом rebase.
Никогда не выполняй push при известных неразрешённых конфликтах.
Никогда не создавай merge commit вместо rebase только потому, что локальная ветка отстала от remote.
Никогда не используй force push без явной необходимости и разрешения пользователя.
Никогда не исправляй уже опубликованный commit через amend и force push без явного разрешения пользователя.
Никогда не считай commit корректным только потому, что команда git commit завершилась успешно.
После создания commit обязательно проверяй фактически сохранённые subject и body.
КЛЮЧЕВОЕ ТРЕБОВАНИЕ
Любой commit обязан содержать:
1. Conventional Commit subject;
2. одну пустую строку;
3. обязательный body;
4. отдельную строку body для каждого файла, фактически вошедшего в commit.
Body должен не просто быть сгенерирован — он должен быть реально записан внутрь Git commit.
После каждого commit это обязательно проверяется через:
git show -s --format=full HEAD
Если в выводе отсутствует body, commit считается выполненным неправильно и должен быть исправлен до push.

## Проверки установленными Codex hooks

- Перед literal commit проверяются Conventional Commit, русский lowercase description из 7–25 слов с глаголом прошедшего времени, одна пустая строка, отдельные неповторяющиеся пункты body и точное совпадение известных файлов index. Для rename указываются старый и новый пути отдельными пунктами; diff читается с `--no-renames`.
- После commit через существующий PostToolUse читаются реально сохранённые subject/body HEAD и файлы через `git diff-tree --root`; первый commit тоже проверяется. Хук не исправляет сообщения и не переписывает историю.
- Перед реальным push одной текущей ветки проверяются исходящие объекты commit, отсутствие конфликтов, незавершённого rebase и отставания от известной remote-tracking ветки (переписанная история допускается с `--force-with-lease` только после отдельной авторизации пользователя). Для новой удалённой ветки проверяются коммиты, отсутствующие в известных refs выбранного remote.
- Push после изменяющих Git-команд в одном shell-вызове запрещён: commit/rebase, проверка результата и push выполняются отдельными вызовами. `--no-verify`, override `core.hooksPath`, обычный force и mirror запрещены. `--force-with-lease` не определяет авторизацию пользователя: её отдельно проверяет агент.
- До staging/commit агент проверяет status, diff, staged diff и релевантный Quality Gate; hooks этого не доказывают. Перед КАЖДЫМ push агент выполняет актуальный fetch + rebase и проверяет восстановление stash. Хук не выполняет сеть и не доказывает свежесть remote-tracking refs или последовательность этих действий.
- Literal shell guard не является shell sandbox: editor/stdin, динамические shell-конструкции и изменение index внутри команды нельзя полностью предсказать до запуска. Их результат проверяется после commit и перед отдельным push. Альтернативные GIT_* repository/index overrides и command-level config overrides для реального push требуют обычного проверяемого вызова.
- Hook проверяет не более 100 исходящих коммитов с ограничением времени; превышение лимита или ошибка чтения блокируют push, а не считаются успешной проверкой. Массовые/tag/URL push требуют отдельного workflow: проверяемая форма — `git push origin <current-branch>`.
- Это глобальные хуки Codex поддерживающего клиента, а не native Git hooks. Они не устанавливают и не перезаписывают Husky, commit-msg, pre-push или core.hooksPath проектов и не контролируют внешний терминал.
